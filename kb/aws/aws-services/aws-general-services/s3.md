# Amazon S3

Amazon S3 (Simple Storage Service): object storage, its core concepts, storage classes and lifecycle rules, and its role as the storage layer of a data lake on AWS.

## What it is

Amazon S3 is storage that treats data as **objects within containers (buckets)**. Each object is a file plus its metadata. Unlike block or file storage, S3 is **standalone**: it isn't tied to compute. You interact with it through API calls (PUT, GET) over HTTPS, rather than mounting a file system.

**Analogy:** a valet parking service. You hand over your entire car (the object), get a ticket (the key), and retrieve the whole car later. You can't swap out the steering wheel while it's parked.

In data engineering, S3 is the foundation of a modern data architecture on AWS. The data lake is built on S3 first, because you need a place to put data before you can ingest it. Every source lands here, processed data is usually written back here, and query engines read from it. For what a data lake is, see [data-lakes-and-warehouses.md](../../../data-engineering/data-lakes-and-warehouses.md).

## Characteristics

- **No editing in place:** to change an object, you download it, change it locally, and upload the whole object again. That trade-off enables:
  - **Massive scalability:** store unlimited objects. You can grow from gigabytes to petabytes seamlessly and without disruption.
  - **High durability:** 11 nines (99.999999999%), with data replicated across at least 3 AZs.
  - **Global access:** retrieve objects from anywhere over HTTPS.
- **Pay for what you use:** per GB stored and per request, with no capacity to provision up front.
- **Stores any data type:** structured, semi-structured and unstructured, as raw files, with no extensive preprocessing.
- **Read by key**, any object, any time. There's no order between objects.
- **Retention is indefinite**, until an object is deleted or moved by a lifecycle rule.
- **Storage only:** S3 doesn't query data itself. An engine such as [Athena](../aws-analytics/athena.md), [EMR](../aws-analytics/emr.md), [Glue](../aws-analytics/glue.md) or Redshift Spectrum reads it, using table definitions from the Glue Data Catalog.
- **Columnar formats:** storing data as Parquet or ORC, with partitioning, makes S3 data cheaper and faster to query with Athena, Redshift Spectrum or EMR.
- **Amazon S3 Tables:** S3 buckets built for tabular data in Apache Iceberg format, with automatic maintenance.
- **Disaster recovery:** cross-Region replication.

### S3 for data lakes

S3 is an optimal foundation for a data lake because of its virtually unlimited scalability and high durability, plus performance, security, and integration with a broad portfolio of analytics, visualization and ML services. On top of the characteristics above:

| Feature | What it adds |
| --- | --- |
| **Scalability** | **Exabyte-scale.** Stores structured (relational), semi-structured (JSON, XML, CSV) and unstructured (images, media) data. Start small and grow with no compromise on performance or reliability |
| **Durability** | S3 Standard copies every object across at least three AZs, which protects against site-level failures. **S3 One Zone-IA keeps copies in one AZ only** |
| **Security** | Identity and access management, inventory scanning, automatic encryption and compliance, across all storage classes |
| **Availability** | Storage classes are designed for **99.5% to 99.99%** availability per year, backed by SLAs |
| **Cost** | Storage is often a significant part of a lake's cost. You pay only for the storage and processing you use |

### Core concepts

- **Bucket:** a container for objects. Its name must be **globally unique** across all accounts and Regions, because it becomes part of a DNS name (`my-bucket.s3.us-east-1.amazonaws.com`). The *name* is global; the *data* is regional. The exception is **directory buckets** (S3 Express One Zone), which are zonal. Their names include the AZ ID (`my-bucket--use1-az4--x-s3`) and only need to be unique within the Region.
- **Object:** a file plus metadata, up to **5 TB** per object. You upload whole objects, and you can't append to an existing one.
- **Key:** the unique identifier within a bucket, for example `photos/2026/vacation.jpg`. The part before the last `/` is the **prefix**. There are no real folders.
  - A bucket is **flat**: `raw/shop/customers/LOAD00000001.parquet` is one key, not a file inside three folders. The console shows folders by grouping keys on the `/` delimiter, and its "Create folder" button only writes an empty object whose key ends in `/`.
  - So "renaming a folder" means copying every object under the prefix to a new key and deleting the old one, and a "folder" disappears once no object uses its prefix.
  - **Partitions are key text too.** In `orders/day=2026-10-27/part-0001.parquet`, S3 sees only a string. Athena, Glue and the Data Catalog read `day=2026-10-27` as a partition value and skip prefixes a query doesn't need. Per-prefix performance limits and event-notification filters also work on this key text.
- **Region:** where the bucket physically resides. S3 is a **regional** service, and data is copied across at least 3 AZs automatically.
- **Versioning:** keeps every version of an object, which protects against overwrites and deletes.
- **Not in your VPC:** S3 has no subnet, ENI or security group. You reach it over the internet (IGW or NAT) or through a free **gateway endpoint**, and control access with IAM and bucket policies.

### Use cases

| Use case | Why S3? |
| --- | --- |
| **Backup and storage** | High redundancy, durability (99.999999999%) |
| **Media hosting** | Unlimited objects, 5 TB per object, web-accessible |
| **Software delivery** | Host downloadable apps and installers |
| **Data lakes** | Store petabytes, pay only for what you use |
| **Static websites** | Host HTML, CSS and JS files directly from S3 |
| **Static content** | Serve images, videos and assets for apps |

### Storage classes

**Choose based on access frequency and durability needs.**

| Storage class | Access pattern | Retrieval time | Use case |
| --- | --- | --- | --- |
| **S3 Standard** | Frequent access | Milliseconds | Active data, websites, apps |
| **S3 Intelligent-Tiering** | Unknown or changing | Milliseconds | Automatically moves data between tiers |
| **S3 Standard-IA** | Infrequent access | Milliseconds | Long-term backups, disaster recovery |
| **S3 One Zone-IA** | Infrequent, non-critical | Milliseconds | Secondary backups, re-creatable data |
| **S3 Glacier Instant Retrieval** | Rarely accessed | Milliseconds | Archive with instant access |
| **S3 Glacier Flexible Retrieval** | 1–2 times a year | 1–5 minutes | Long-term archives |
| **S3 Glacier Deep Archive** | Rarely or never | 12 hours | Regulatory compliance (7–10 years) |

- Retrieval times depend on the retrieval tier: Glacier Flexible Retrieval is 1–5 minutes expedited, 3–5 hours standard and 5–12 hours bulk. Deep Archive is within 12 hours standard and within 48 hours bulk.

**Rule of thumb:**

- Active data → **Standard**
- Don't know? → **Intelligent-Tiering** (auto-optimizes)
- Backups → **Standard-IA** or **One Zone-IA**
- Archives → **Glacier** variants

### Lifecycle rules

A **lifecycle configuration** is a set of rules on a bucket that act on objects **automatically, by age**. A rule applies to the whole bucket or to objects filtered by prefix, tag or size, and takes two kinds of action:

- **Transition:** move objects to a cheaper storage class after N days, for example Standard → Standard-IA after 30 days → Glacier Flexible Retrieval after 365.
- **Expiration:** delete objects after N days.

On versioned buckets, rules can also transition or expire **noncurrent versions**. Rules can also clean up **incomplete multipart uploads** and expired delete markers, which otherwise sit in the bucket and cost money.

**Why they're useful:**

- **Cost:** most data is read heavily when new and rarely later. Rules move it down the storage classes as it cools, with no code, jobs or manual moves.
- **Retention:** expiration enforces "keep for N years, then delete", for compliance or to stop paying for data nobody needs.
- **Housekeeping:** temporary prefixes (staging, scratch), old object versions and failed uploads get cleaned up on their own.

In a data lake, lifecycle rules usually go on the raw and cleaned buckets, which are rarely read once their data is curated, while the curated bucket uses Intelligent-Tiering. The Example Corp example below shows the course's setup. Expiring raw files also deletes the history they hold ([replicating-databases-to-the-lake.md](../../../data-engineering/replicating-databases-to-the-lake.md)).

### Data lake zones on S3

Each zone of the lake is commonly its **own S3 bucket**: raw, cleaned and curated, plus optional landing, logs, archived and sandbox buckets. The zones themselves are defined in [data-lake-zones.md](../../../data-engineering/data-lake-zones.md). S3-specific choices per zone:

| Bucket | S3 setup |
| --- | --- |
| **Raw** | **Turn on versioning**, to preserve data integrity. S3 Standard while active, then lifecycle rules |
| **Cleaned** | S3 Standard while active, then lifecycle rules |
| **Curated** | **S3 Intelligent-Tiering**, so many consumers with different access patterns need no rules |
| **Landing** | Holds sensitive data (PII) until it's masked and moved to raw |
| **Logs** | S3 server access logs, CloudWatch log files and CloudTrail log files |

**Watch for** _(verify)_:

- **Minimum storage durations:** about 30 days for Standard-IA and One Zone-IA, 90 for Glacier Instant and Flexible Retrieval, and 180 for Deep Archive. Deleting or moving an object earlier is billed as if it stayed that long.
- **Many small objects:** each transition is a billed request, and by default objects under 128 KB aren't transitioned. Lakes with millions of tiny files gain little.
- **Not instant:** rules run in the background, roughly once a day.
- **Lifecycle vs Intelligent-Tiering:** lifecycle rules suit a known, age-based pattern ("logs are cold after 90 days"). Intelligent-Tiering suits unknown or changing access, and moves objects for you based on actual use.

### Security

- **Controls:** Block Public Access, bucket policies, encryption (SSE-S3 by default, SSE-KMS, SSE-C), Object Lock and MFA Delete.
- **Bucket policy:** a **resource-based policy** on the bucket, so it **must name a `Principal`**. That can be:
  - an account
  - a role
  - a service such as `cloudfront.amazonaws.com` (OAC, with an `AWS:SourceArn` condition)
  - `"*"`, but only with a condition such as `aws:PrincipalOrgID`, or in a `Deny` such as "deny if `aws:SecureTransport` is false"
- **Cross-account access** needs both the bucket policy **and** the caller's IAM policy, plus the [KMS](../aws-security/kms.md) key policy if the bucket uses SSE-KMS.
- **ARNs:** `s3:ListBucket` uses the bucket ARN, while `s3:GetObject` uses `bucket/*`.
- In data pipelines: default bucket encryption with a customer managed key, and a bucket policy that denies non-HTTPS requests. [Macie](../aws-security/macie.md) scans buckets for PII.

### Performance

- **3,500 writes and 5,500 reads per second per prefix.** S3 scales automatically with unlimited prefixes, but a sudden spike can return **503 Slow Down**. Retry with backoff.
- Multipart upload, Transfer Acceleration and byte-range fetches speed up large transfers.

### Event notifications

- Events such as `ObjectCreated` (an overwrite counts) and `ObjectRemoved`, with prefix and suffix filters, can go to [Lambda](../aws-compute/lambda.md), [SQS](../aws-application-coordination/sqs.md), [SNS](../aws-application-coordination/sns.md) or [EventBridge](../aws-application-coordination/eventbridge.md).
- This makes S3 the usual starting point of a serverless pipeline.

### Static websites

Serverless applications often use S3 for file storage and for **hosting static websites**: HTML, CSS, JavaScript and images served directly from a bucket. Put **CloudFront with OAC** (origin access control) in front of the bucket.

S3 **can't** host:

- Server-side rendered applications (SSR)
- Traditional backend applications (PHP, Rails, Django)
- Applications that run server-side code per request

Modern **SPAs** can still run on S3:

- Host the static front-end files on S3.
- Use separate backend services ([Lambda](../aws-compute/lambda.md), [API Gateway](../aws-apis/api-gateway.md)) for dynamic functionality.
- Fetch data with API calls from the client.

Trade-offs:

- ✅ Can build complex apps (e-commerce, social media, and so on).
- ❌ SEO challenges (without SSR or SSG).
- ❌ Initial load performance (large JS bundles).

## Example

- **Addressing an object:**

  ```
  Bucket: my-app-uploads
  Key:    users/123/profile.jpg
  URL:    https://my-app-uploads.s3.us-east-1.amazonaws.com/
          users/123/profile.jpg
  ```

- **API calls** (boto3):

  ```python
  # Upload an object
  s3.put_object(
      Bucket='my-bucket',
      Key='documents/report.pdf',
      Body=file_data,
      StorageClass='STANDARD_IA'  # Choose storage class
  )

  # Retrieve an object
  response = s3.get_object(
      Bucket='my-bucket',
      Key='documents/report.pdf'
  )
  ```

- **Lifecycle:** application logs land in S3 Standard. A Lifecycle rule moves them to Glacier Flexible Retrieval after 90 days and deletes them after 7 years.
- **Example Corp's data lake:** Example Corp splits its lake across three S3 buckets (raw, cleaned, curated) and picks storage per zone, to comply with industry regulations and optimize costs.

  | Zone | Storage | Why |
  | --- | --- | --- |
  | Raw | S3 Standard, then lifecycle rules | Well suited to high-transaction workloads while active; rarely accessed once curated |
  | Cleaned | S3 Standard, then lifecycle rules | Same as raw |
  | Curated | S3 Intelligent-Tiering, no lifecycle rules | Moves data to the most cost-effective tier as it cools, with no rules to manage for the many consumers and use cases |

  The lifecycle rules on the raw and cleaned buckets, for archiving:

  1. After **1 year**, move all files to **S3 Standard-IA**.
  2. After **2 years in Standard-IA**, move them to **S3 Glacier Deep Archive**.
  3. After **7 years in Deep Archive**, **expire** (delete) the data.

  ```
  Standard ─1 yr─► Standard-IA ─+2 yrs─► Deep Archive ─+7 yrs─► gone
  (created)         (year 1)             (year 3)              (yr 10)
  ```

  When configured, rules count days since the object was created, so these are day 365, day 1,095 and expiry at day 3,650.
- **Data lake flow**: raw data from every source lands in S3. Glue or EMR transforms it, and the curated output stays in S3. The hot, heavily queried subset goes into [Redshift](../aws-analytics/redshift.md), or is queried in place with Athena or Spectrum.
- **Serverless portal**: an internal data-quality portal has no server to manage anywhere.
  - The React front end is a static website in S3 behind CloudFront.
  - Its buttons call [API Gateway](../aws-apis/api-gateway.md) → Lambda, which reads results from [DynamoDB](../aws-databases/dynamodb.md).
  - Users upload CSV files to a bucket, and each upload triggers a Lambda function.
